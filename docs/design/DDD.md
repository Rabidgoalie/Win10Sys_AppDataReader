# Database Design Document (DDD): Windows 10 Disaster Recovery Application

## 1. Storage Strategy

The application uses SQLite for active session persistence and structured JSON for portable report exports.

A report export serializes the full evidence package:

- session metadata;
- sources;
- user profiles;
- application records;
- evidence records;
- application-to-evidence links;
- user-data findings;
- warnings;
- schema version.

A report import rehydrates those records into a TRIAGE-mode session.

The database does not store file contents.

Timestamps shall be stored as UTC ISO-8601 strings.

Report files shall be UTF-8 encoded.

## 3. Entity Descriptions

### `SCAN_SESSION`

Represents one recovery scan session or one loaded report session.

### `SCAN_SOURCE`

Represents one source used in the session.

A source is either:

- a mounted block device prepared by the application;
- a manifest file generated from a block device or supplied by the user.

Externally mounted paths are not supported.

Manifest-only sources are secondary sources.

### `USER_PROFILE`

Represents a Windows user profile discovered on a Windows source.

### `APP_RECORD`

Represents a correlated application identity.

Application records are source-scoped.

### `DISCOVERY_EVIDENCE`

Represents one raw evidence item.

Evidence is first-class.

It may be linked to zero, one, or multiple application records through `APP_EVIDENCE`, subject to source-scoping rules.

### `APP_EVIDENCE`

Links evidence to application records.

An application may only be linked to evidence from the same source.

### `USER_DATA_FINDING`

Represents a potential user-generated-content location.

Findings may be associated with an application, a user profile, both, or neither.

A finding is uniquely identified within a session and source by its normalized path.

### `SESSION_WARNING`

Represents a user-visible warning generated by acquisition, parsing, correlation, heuristics, I/O failure, or report handling.

Source constraints:

```text
CHECK (
  (source_type = 'mounted_block_device' AND acquisition_method = 'ntfs3g_ro')

  (source_type = 'manifest_file' AND acquisition_method = 'ntfsls_manifest')
)
```

`mount_point` may be NULL while a mounted-block-device source is pending or has failed preparation.

`manifest_path` may be NULL while a manifest-file source is pending or has failed preparation.

When a source is ready or complete, the corresponding `mount_point` or `manifest_path` shall be present.

## 5. Evidence Hash Strategy

The `evidence_hash` prevents duplicate evidence rows and avoids reliance on nullable-column unique constraints.

The application shall compute `evidence_hash` deterministically using SHA-256 over canonical evidence identity fields.

The canonical field order is:

1. `source_id`
2. `evidence_type`
3. `hive_file_path`
4. `root_hive`
5. `key_path`
6. `value_name`
7. `value_data_hash`
8. `user_sid`
9. `normalized_path`
10. `product_code`

Canonicalization rules:

- UTF-8 encoding shall be used for the hash input.
- Fields shall be joined using ASCII unit separator character `0x1F`.
- NULL fields shall become empty strings.
- `source_id` shall be preserved as a lowercase UUID string.
- `evidence_type` shall be preserved exactly.
- `hive_file_path` shall be normalized to a source-relative logical path and lowercased.
- `root_hive` shall be uppercased.
- Registry `key_path` shall be normalized to backslash-separated form, without leading or trailing backslash, and lowercased.
- `value_name` shall be lowercased.
- `user_sid` shall be uppercased.
- `normalized_path` shall be normalized to backslash-separated Windows-style form and lowercased.
- `product_code` shall be normalized to uppercase GUID form without braces unless the original identifier is not a GUID.

`value_data_hash` shall be computed as follows:

- If `value_data` is absent, `value_data_hash` is empty.
- If present, the application shall compute SHA-256 over a canonical type-prefixed representation.
- The type prefix shall identify the registry value type.
- String values shall be normalized for trailing NUL characters but shall preserve meaningful line breaks.
- Numeric values shall be canonical decimal strings.
- Binary values shall be canonical lowercase hexadecimal strings.

The stored `value_data` column shall contain a safe textual representation suitable for UI display and report export, not file contents.

## 6. Application Identity Hash Strategy

`APP_RECORD.identity_hash` shall be computed deterministically using SHA-256 over:

1. `source_id`
2. `identity_basis`
3. `identity_key`

Fields shall be joined using ASCII unit separator `0x1F`.

`identity_key` normalization depends on `identity_basis`:

- `product_code`: uppercase normalized product code.
- `uninstall_key`: normalized registry key path.
- `install_path`: normalized install path.
- `name_publisher_version`: normalized display name, publisher, and version joined by unit separators.
- `portable_directory`: normalized portable root path.
- `manifest_directory`: normalized manifest-derived directory path.
- `executable_bundle`: normalized executable-bundle path or name.
- `fallback`: deterministic normalized evidence-derived key.

The correlator shall choose the strongest available identity basis.

Recommended indexes:

```text
CREATE INDEX idx_source_session ON SCAN_SOURCE(session_id);
CREATE INDEX idx_profile_session ON USER_PROFILE(session_id);
CREATE INDEX idx_profile_source ON USER_PROFILE(source_id);
CREATE INDEX idx_app_session ON APP_RECORD(session_id);
CREATE INDEX idx_app_source ON APP_RECORD(source_id);
CREATE INDEX idx_app_session_name ON APP_RECORD(session_id, display_name);
CREATE INDEX idx_evidence_session ON DISCOVERY_EVIDENCE(session_id);
CREATE INDEX idx_evidence_source ON DISCOVERY_EVIDENCE(source_id);
CREATE INDEX idx_evidence_type ON DISCOVERY_EVIDENCE(evidence_type);
CREATE INDEX idx_app_evidence_app ON APP_EVIDENCE(app_id);
CREATE INDEX idx_app_evidence_evidence ON APP_EVIDENCE(evidence_id);
CREATE INDEX idx_finding_session ON USER_DATA_FINDING(session_id);
CREATE INDEX idx_finding_app ON USER_DATA_FINDING(app_id);
CREATE INDEX idx_finding_profile ON USER_DATA_FINDING(profile_id);

```

The unique constraint on `DISCOVERY_EVIDENCE.evidence_hash` provides its own index.

## 8. Report Export Structure

The JSON report shall include:

```json
{
  "schema_version": "1.0.0",
  "session": {},
  "sources": [],
  "user_profiles": [],
  "applications": [],
  "evidence": [],
  "app_evidence_links": [],
  "user_data_findings": [],
  "warnings": []
}
```

Application records in the report shall include `source_id`, `identity_basis`, and `identity_key`.

The report shall preserve original identifiers.

The report shall not include file contents.

Report import shall validate `schema_version` before hydration.

---

## 9. Report Import Rules

Report import shall:

1. Validate schema compatibility.
2. Reject malformed JSON.
3. Reject incompatible schema versions.
4. Safely release active source access.
5. Replace the current session state.
6. Preserve original IDs.
7. Hydrate all tables.
8. Enter Triage Mode.

If a uniqueness conflict occurs during hydration, the import shall fail with an actionable error rather than silently overwriting local triage state.

---

## 10. Concurrency and Transaction Notes

SQLite access shall be serialized through the persistence layer.

The persistence layer shall:

- enable foreign key enforcement on every connection;
- serialize write transactions;
- use periodic commits during long scans;
- support bounded batch inserts;
- commit triage edits promptly;
- avoid exposing database connections directly to UI widgets.

Background workers shall not write to the UI directly.

UI triage edits shall be persisted through the same persistence layer used by scan workers.
